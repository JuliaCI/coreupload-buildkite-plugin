Bound core processing and uploads per job

When a test crashes repeatedly, the plugin processes every core at once. On the Apple M6 Macs (julia-pr builds 5607 and 5609), ~8 test workers per job aborted and left cores of 5-62 GB each. The plugin compressed all 8 in parallel and started all 8 uploads at once (~2.2 GiB each, 10 multipart parts per artifact). That took ~30 of the job's 46 minutes. The compressors starved lldb, so the watchdog killed `bt all` on the first core, the most useful one, before it printed anything. The 80 concurrent PUTs saturated the site's <100 Mbit/s uplink, which stalled builds on other hosts, and outlived Buildkite's presigned part URLs (`X-Amz-Expires: 368`). buildkite-agent then retried the expired URLs with 403s until someone cancelled the job.

Now cores are handled oldest first (by modification time): the first crash is the likeliest root cause, and a crash that keeps repeating adds little. The debugger commands run on the `max_cores` oldest cores (default 10). Only the `max_uploads` oldest (default 1) are compressed and uploaded, one at a time, still in the background while the debugger runs. Each upload is killed after `upload_timeout` (default 900 s), so an expired URL no longer hangs the job. A host can lower the upload count by setting `COREUPLOAD_MAX_UPLOADS` in its environment, e.g. `0` on a site with a slow uplink. A core is skipped when compressing it (assuming no compression at all) would leave less than 5 GiB of free disk space. Cores and bundles are deleted at the end, so they don't fill the disk for the next job on the host.

The debugger watchdog also had bugs: it killed the bash subshell around the debugger, not the debugger, and stayed armed after the debugger finished, so it printed "DEBUGGER KILLED BY WATCHDOG TIMER" and signalled a possibly reused PID 120 s later. All debugger calls, including the image listing used for bundles, now go through one timeout helper that kills the debugger and its direct children and reports only real kills.

I didn't dedupe cores by crash signature. Parsing frames out of gdb/lldb output is fragile, and here every core would have collapsed to the same abort frames anyway, so a count limit does the same job. buildkite-agent's `--concurrency` doesn't help either: it doesn't extend URL lifetimes, and parts that start later are more likely to see expired URLs.

The only user is JuliaCI/julia-buildkite. Defaults change (one upload instead of all) but no options are needed there. The plugin's own CI check now expects 2 julia cores instead of 3, since the gdb step crashes twice and uploads only its oldest core.

Tested locally with `test/post-command.sh`, which runs the hook against fake cores with doubles for lldb, buildkite-agent and df: ordering, both limits, the host override, a hanging debugger, a hanging upload and low disk. All 7 cases pass here and fail on main. Not yet run on real cores on Linux or FreeBSD.
